🌿 Control de versiones

Cómo llevar el historial de cambios de un proyecto y trabajar en equipo sin perder código.

Definición de control de versiones

El control de versiones es un sistema que registra los cambios que se hacen a uno o varios archivos a lo largo del tiempo, de forma que después se puede regresar a una versión anterior, comparar cambios, ver quién modificó algo y cuándo lo hizo.

En el desarrollo de software se usa para guardar el código fuente de un proyecto. A cada "foto" del proyecto en un momento dado se le llama versión o commit, y al lugar donde se guarda todo el historial se le conoce como repositorio.

💡 En pocas palabras: es como el "Ctrl + Z" de todo un proyecto, pero con historial completo y pensado para que varias personas trabajen al mismo tiempo.

¿Cuáles son? (tipos de sistemas)

Los sistemas de control de versiones (VCS, por sus siglas en inglés) se dividen en tres tipos:

1. Sistemas locales

Guardan el historial de cambios en la misma computadora donde se trabaja, normalmente en una pequeña base de datos con las diferencias entre versiones. Un ejemplo clásico es RCS (Revision Control System). Sirven para una sola persona, pero no permiten colaborar.

2. Sistemas centralizados (CVCS)

Hay un servidor central que guarda todas las versiones, y cada programador se conecta a él para descargar (checkout) y subir (commit) sus cambios. Ejemplos: CVS, Subversion (SVN) y Perforce.

3. Sistemas distribuidos (DVCS)

Cada desarrollador tiene una copia completa del repositorio con todo el historial en su computadora. Se puede trabajar sin internet y después sincronizar con otros repositorios (por ejemplo, uno remoto en GitHub). Ejemplos: Git, Mercurial y Bazaar. Hoy en día Git es el más usado.

Funcionamiento

Tomando como ejemplo Git, un proyecto pasa por tres áreas principales:

  1. Directorio de trabajo: la carpeta donde editamos los archivos normalmente.
  2. Área de preparación (staging): aquí se agregan con git add los cambios que queremos incluir en la siguiente versión.
  3. Repositorio: con git commit se guarda una "foto" de lo que está en staging, con un mensaje, autor y fecha. Cada commit tiene un identificador único (hash).

Además, se pueden crear ramas (branches) para trabajar en algo nuevo sin afectar la rama principal (main). Cuando el trabajo está listo, la rama se fusiona (merge) con la principal. Para compartir el código se usa un repositorio remoto (GitHub, GitLab, Bitbucket) con los comandos git push (subir) y git pull (bajar).

Uso en el rastreo y gestión de cambios

El control de versiones permite llevar un control detallado de todo lo que pasa en el proyecto:

  • Historial: con git log se ve la lista de cambios, quién los hizo, cuándo y por qué (el mensaje del commit).
  • Comparar versiones: git diff muestra exactamente qué líneas se agregaron o eliminaron.
  • Saber quién cambió una línea: git blame indica el autor y el commit de cada línea de un archivo.
  • Deshacer errores: git revert o git restore permiten regresar a un estado anterior.
  • Trabajo en paralelo: cada integrante trabaja en su propia rama y luego se revisa el código mediante Pull Requests antes de unirlo.
  • Versiones de entrega: con git tag se marcan versiones importantes, por ejemplo v1.0 de una app publicada.
  • Resolución de conflictos: si dos personas modifican la misma línea, Git avisa del conflicto para que se decida qué cambio conservar.

Ejemplos

Ejemplo 1: crear un repositorio y hacer el primer commit
bash
git init                      # crea el repositorio en la carpeta actual
git add index.html            # agrega el archivo al área de preparación
git commit -m "Primera versión de la página"
git log --oneline             # muestra el historial
Ejemplo 2: trabajar con ramas
bash
git branch login              # crea la rama "login"
git switch login              # se cambia a esa rama
# ... se hacen cambios y commits ...
git switch main               # regresa a la rama principal
git merge login               # une los cambios de "login" en "main"
Ejemplo 3: subir el proyecto a GitHub
bash
git remote add origin https://github.com/usuario/mi-app.git
git push -u origin main       # sube la rama main al repositorio remoto
git pull                      # descarga los cambios de los compañeros
Ejemplo 4: Subversion (centralizado)
bash
svn checkout http://servidor/svn/proyecto   # descarga la copia de trabajo
svn update                                  # trae los cambios del servidor
svn commit -m "Corrige error en el menú"    # sube los cambios al servidor
